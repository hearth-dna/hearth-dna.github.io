# ADR 0010: the mobile apps become native apps

**Date:** 2026-09-21 · **Status:** Accepted · **Supersedes:** [0006](0006-native-shells-around-the-pwa.md) (since 2026-09-23, see *Outcome*)

## Context

ADR 0006 made the phone apps web views around the PWA and said they would be "as good as the web
app is on a small screen, and no better". In use that ceiling is too low: the health log on an
Android phone reads as a web page in a frame — HTML controls sized up to touch targets, cards
inside cards, no navigation drawer, sheet, search bar or floating button behaving the way the rest
of the phone does. Responsive CSS narrows the gap but cannot close it.

The alternatives weighed:

- **A shared Kotlin Multiplatform core** under Compose and SwiftUI screens: two implementations of
  the data layer (TypeScript for the web, Kotlin for both phones).
- **The TypeScript core in a headless JS engine** under native screens: one implementation, but
  SQLite, files and crypto re-plumbed across two runtimes on each platform.
- **Separate native apps**: Kotlin on Android, Swift on iOS, each with its own data layer.

The project chose the third: each app is written in its platform's own language and toolkit only,
with no cross-platform framework to learn, upgrade or debug through.

## Decision

- **Android** is Kotlin with Jetpack Compose and Material 3. **iOS** is Swift with SwiftUI. No
  web view, no shared runtime, no cross-platform UI or core framework.
- **Each app owns a native data layer** in its own language: the SQLite schema of
  `frontend/src/db/schema.ts`, verbatim, in an app-private database (Android's framework SQLite,
  iOS's system `libsqlite3`), and ports of the pure logic modules (`health/log.ts` first).
- **The dump v2 container is the contract between the three.** A backup written by any of them
  restores in the other two, byte format and journal rows alike
  (`docs/architecture/storage/dump-v2.md`). Golden files generated by the web code live in
  `mobile/fixtures/` and every implementation's tests read them; the schema text is checked against
  `schema.ts` the same way. Drift between the three shows up as a failing test, not a lost backup.
- **One string catalogue.** `frontend/src/i18n/` stays the only place text is written and
  translated; `make mobile-i18n` copies the JSON into both apps, which interpolate `{name}` exactly
  as the web does. Twenty languages are not maintained three times.
- **The privacy rules carry over unchanged.** ADR 0001, 0007 and 0009 apply to the native code as
  written: no server, the only destinations are the provider the user brings a key for and the
  cloud drive they sign in to, and each app routes every network call through one type
  (`Egress.kt`, `Egress.swift`) with a test that nothing else opens a connection.

## Staging

The port goes screen by screen, and the current app keeps working throughout:

1. The native screens are a second entry point beside the web view: on Android a debug-only
   launcher activity ("Hearth native"), on iOS a debug-only scene. Their database is their own and
   starts empty; restoring a backup fills it.
2. The first slice is the **Health log** (browse, filter, sort, add, delete) plus **restore a
   backup**, so it shows real data from day one. Then People and genome import, Family, Lookup,
   Ask, Settings with export, backups and cloud drives.
3. At parity the web view, `WebViewAssetLoader`/`LocalWebServer`, the JS bridges and
   `make mobile-web` are deleted, the native entry point becomes the launcher, the store listing
   updates in place (same identifiers), and 0006 is marked Superseded. A user's web-view database
   moves across with one backup-and-restore, offered on first launch of the native build.

## Consequences

- **Three implementations of the code that must not be wrong** — the price 0006 refused to pay.
  The fixtures and schema checks are what make it payable; a format change lands in all three in
  the same commit or not at all.
- **Every feature is built three times** (web, Compose, SwiftUI). The web app remains the reference
  for behaviour; the phones are the reference for how it should feel.
- **iOS needs macOS to build.** Swift written on another machine is unverified until it has gone
  through Xcode and the tests there.
- **Revisit if** keeping the three in step costs more than it buys: the Kotlin Multiplatform core
  is the fallback, and would replace the two native data layers without touching either UI.

## Outcome (2026-09-23)

The port reached parity screen by screen: People and genome import, the person report, Family
lookup, Ask, attachments and document reading, Settings with export, open formats and backups to a
folder, a file or a cloud drive. The HTML archive export was left out on purpose: it is a way to
carry the web app itself.

- **No migration.** There were no users of the web-view apps, so the first-launch
  backup-and-restore in *Staging* step 3 was not built. The web view, its asset server, the JS
  bridges and `make mobile-web` are deleted; the native activity and scene are the apps.
- **The contract held.** Backups written by the web, by Android and (once built on a Mac) by iOS
  open in the other two; `mobile/fixtures/` carries a file from each writer, and a folder backup
  written on the Android emulator was read back by the web code.
- **iOS is unverified** until it has been built and tested in Xcode; everything Swift in the port
  was written without a Mac.
